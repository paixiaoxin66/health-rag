## 写在前面：本文的核心思想

本文要回答三个递进的问题，这也是本次分享的行文顺序：

1. **RAG 为什么要这样运行？** —— 先理解原理
2. **我们为什么选择这些技术？** —— 再理解选型
3. **我们如何把它写出来？** —— 最后看实战

贯穿全篇的核心思想是 **"两阶段"** 的 RAG 运行方式：

> **提问前（离线 · 备课阶段）**：知识库内部完成给定文档的切分（chunk）、向量化（embedding）、入库建索引等预处理；
> **提问后（在线 · 推理阶段）**：把用户问题向量化，与向量数据库做语义相似度匹配，对匹配到的候选进行重排、取出相似度最高的几条，组装成上下文交给大模型，由大模型基于这些资料生成答案返回给用户。

一句话概括：**让大模型"开卷考试"——从私有知识库里检索可信资料，再基于资料作答。**

# 第一讲：RAG 为什么要这样运行

## 1.1 问题的起点：大模型的三个局限

要理解 RAG，先理解它解决什么。大模型（LLM）再强大也有三个先天局限：

| 局限 | 说明 | 后果 |
|---|---|---|
| **知识有截止日期** | 训练数据只到某个时间点 | 问"最近发生的事"会答错或答不出 |
| **会产生幻觉** | 不会的就"编"，且语气极其自信 | 专业场景下不可信、有风险 |
| **不知道你的私有知识** | 训练时没见过你的文档/数据 | 问自己的资料库等于没问 |

**三个局限的本质是同一个：模型的知识 = 训练时见过的数据，而我们需要的是"模型 + 我们的私有知识"。**

怎么把"我们的知识"交给模型？两个极端方案：
- **微调（Fine-tuning）**：把知识"炼"进模型权重 —— 贵、慢、每次改资料都要重训，且更新不及时
- **RAG（检索增强生成）**：把知识放在模型"旁边"，用的时候查出来喂给模型 —— 便宜、灵活、可溯源

RAG 的思路像给模型配了一个**随时可翻阅的资料库 + 检索员**。这就是它"为什么要这样运行"的根本原因。

## 1.2 核心思想：两阶段

RAG 天然分成两个阶段，**本质区别在于"问题是否已知"**：

- **提问前（离线）**：问题未知，先不管用户问什么，把知识库**预处理好**，随时待命
- **提问后（在线）**：问题来了，用预处理好的索引**快速找到相关资料**，辅助生成

这个划分决定了整个架构。下面拆开讲。

## 1.3 提问前：知识库如何"备课"

用户还没来提问，知识库要把原始文档变成"可被检索的形态"，四个动作：

### ① 切分（Chunking）—— 把长文档切成小块

一份文档可能几万字，为什么不能整篇拿去检索？
- **最小可检索单元**：检索时命中的应该是一段"能回答问题"的内容，而不是整篇文档（命中粒度太粗，答案会淹没在无关文字里）
- **模型上下文有限**：LLM 一次能处理的内容有限，塞不进整篇文档
- **相似度更聚焦**：小块文本的向量更能精准表达语义

> 实践经验：chunk 大小（如 500 字）+ 重叠（overlap 50 字）要平衡——太大检索不准，太小丢上下文。切分时尽量保留语义边界。

### ② 向量化（Embedding）—— 把文本翻译成"语义坐标"

**关键洞察：文字无法直接比相似度，但向量可以。**

Embedding 模型把一段文本编码成一个向量（一串数字），**语义相近的文本，向量在空间里也靠得近**。这就是"语义检索"的基础：

- 传统关键词检索："苹果" 匹配不到 "水果"，字面对不上就找不到
- 语义向量检索：意思相近就能命中，即使字面不同（"降压"↔"控制血压"）

```
"高血压患者要少吃盐"  →  [0.23, -0.45, 0.11, ...]  (512 维向量)
"盐分摄入过多会导致血压升高" → [0.25, -0.42, 0.09, ...]  (离得很近 ✓)
```

### ③ 入库 + 构建索引 —— 让"大海捞针"变成"秒级检索"

向量数量一多（上万条），逐条暴力比对就太慢了。向量数据库为向量建 **ANN 索引（如 HNSW）**，把"全库扫描"变成"邻近搜索"，毫秒级返回相似向量。

**一句话总结备课阶段：文档 → 切块 → 向量化 → 建索引。这是一次性预处理，做完即可长期待命。**

## 1.4 提问后：一次问答的旅程

用户问了一个问题，RAG 的在线链路：

### ① 问题向量化（不是"提取关键词"）

**最容易误解的一步**：RAG 不是用大模型提取问题里的关键词去匹配。

问题要被检索，就得和知识库"同一种语言"——**用同一个 embedding 模型把问题也编码成向量**（query vector），再去向量库里找"语义上离它最近的 chunk"。这是语义匹配，不是关键词匹配。

### ② 召回（Recall）—— 先从库里捞一网"候选"

用问题向量在向量库里做最近邻搜索，捞出 **Top-K 条**（如 20 条）最相似的 chunk。

这一步的模型叫 **bi-encoder（双塔）**：问题和文档**分别**编码成向量，用向量相似度排序。优点：快（能预先算好库里的向量）；缺点：粗（问题和文档分开编码，交互不够充分）。

### ③ 重排（Rerank）—— 精挑细选

召回捞的是"可能相关"的 20 条，但相关性有高有低。**直接全塞给模型会引入噪声**，所以要用更准的模型重新打分：

- 重排模型是 **cross-encoder（交叉编码器）**：把"问题 + chunk"**拼在一起**过一遍模型，做深度交互后给出精准的相关性分数
- 从 20 条里取出 **Top-k 条**（如 5 条）真正高质量的

**为什么两级而不一步到位？** 因为"准的模型慢、快的模型粗"——先用便宜的召回过滤到 20 条，再用贵的重排精挑到 5 条，**性价比最优**（相当于先海选再决赛）。

### ④ 组装上下文 + 生成 —— RAG 的灵魂

**检索结果不是直接返回给用户，而是进入"生成"环节：**

1. 把命中的 chunk 按相关性组装成**上下文（Context）**
2. 与用户问题一起拼进**提示词（Prompt）**：*"基于以下资料回答问题……[资料]……问题：……"*
3. **大模型基于这些资料生成答案**，并可标注引用来源

这一步就是 RAG 的灵魂——**让模型"有依据地作答"**：资料是检来的真实内容，答案就不容易编（降幻觉），还能告诉用户"我凭什么这么答"（可溯源）。

### ⑤ 返回：答案 + 来源 + 分步追踪

最终返回的不只是答案，而是**答案 + 引用来源 + 分步 trace**（每一步的状态与耗时）。这就是"有迹可循"——每一次回答都知道它基于哪些资料、每步花了多久，线上出问题能立刻定位。

## 1.5 一张图总结两阶段

```
┌──────────── 提问前（离线 · 备课） ────────────┐
│  文档 → Chunk 切分 → Embedding 向量化          │
│  → 向量数据库（构建索引）                      │
└───────────────────────────────────────────────┘
                    ↓
┌──────────── 提问后（在线 · 推理） ────────────┐
│  问题 → 同模型向量化 → 向量库召回 Top-20       │
│  → Reranker 精排 Top-5 → 组装上下文            │
│  → Prompt → LLM 基于资料生成答案               │
│  → 返回 [答案 + 来源 + 分步 trace]             │
└───────────────────────────────────────────────┘
```

# 第二讲：我们为什么选择这些技术

理解了"为什么这样运行"，再看"为什么选这些技术"就顺理成章了——**每一项选择都在回答第一讲的某个环节**。

## 2.1 选型总览

| 环节 | 技术选型 | 一句话理由 |
|---|---|---|
| Embedding | `BAAI/bge-small-zh-v1.5`（本地） | 中文语义强、512 维轻量、CPU 可跑、数据不出本机 |
| 向量数据库 | **ChromaDB** | 轻量嵌入式、零运维、本地文件存储、够用 |
| 重排 | `BAAI/bge-reranker-base`（本地） | 中文 cross-encoder，召回+重排两级架构的关键 |
| LLM | DashScope `deepseek-v4-flash`（API） | 小机器跑不动大参数本地 LLM，API 性价比最高 |
| Web 框架 | **FastAPI** | 异步、自动文档、类型安全、生产成熟 |
| 可观测 | 结构化日志 + request_id | 有迹可循，生产排障刚需 |

## 2.2 为什么本地 Embedding？

- **隐私**：健康数据是最敏感的数据之一，向量化在**本机**完成，文本不出内网
- **成本**：embedding API 按量收费，量大就贵；本地跑免费
- **够用**：`bge-small-zh-v1.5` 512 维，CPU 上单条毫秒级，已足够支撑私有知识库规模
- **离线**：模型下载后 `local_files_only` 全离线运行，不依赖外网

> 原则：**凡是能本地化且本地够用的，就本地化**——这正是"私有化"的含义。

## 2.3 为什么 ChromaDB？

- 相比 ES / Milvus / Qdrant 等重引擎，ChromaDB 是**嵌入式**（像 SQLite 之于 MySQL）——零部署、单文件、随应用走
- 满足本项目规模（万级 chunk）绰绰有余
- 后续如果规模暴涨，接口抽象可平滑迁移到更强引擎

> 原则：**技术选型匹配问题规模，不为"高大上"买单。**

## 2.4 为什么"召回 + 重排"两级？

这是第一讲 1.4 的直接落地：
- **召回用 bi-encoder**：快、能扛全库，但粗
- **重排用 cross-encoder**：准，但慢、只能处理小批量

两级配合 = 以最小成本拿到"既全又准"的结果。这是工业级 RAG 的标准做法。

## 2.5 为什么 LLM 走 API 而非本地？

- 部署目标是小机器——本地跑大参数模型不现实（内存、推理速度都不够）
- API 方案：模型在云端、按量付费、无需硬件投入，且 `deepseek-v4-flash` 中文生成质量好
- 数据流向：**只有"检索到的上下文 + 问题"发给云端 LLM**，原始语料仍在本机

> 权衡：私有化程度 ≠ 全本地。**在"敏感数据不出本机"和"算力成本"之间取平衡**——核心知识留在本地，生成算力交给 API。

## 2.6 为什么 FastAPI + 结构化日志？

- FastAPI：Pydantic 数据校验 + 自动 OpenAPI 文档（`/docs` 白送）+ 异步支持，封装 API 的首选
- 结构化日志（JSON Lines）+ **request_id 贯穿全链路**：一次请求从检索到生成的所有日志可串联，配合每次问答返回的 `steps` trace，"有迹可循"落到实处

## 2.7 选型原则小结

1. **匹配问题规模**，不为炫技买单
2. **能本地化就本地化**（隐私 + 成本）
3. **粗排 + 精排两级**，性价比优先
4. **生成算力走 API**，核心数据不出本机
5. **一切可观测**，有迹可循

# 结语

回到开篇的核心思想：

> **RAG = 提问前把知识库备好课（切块 + 向量化 + 建索引），提问后让模型有依据地作答（召回 + 重排 + 基于资料生成）。**

本文用"为什么运行 → 为什么选这些技术 → 怎么写出来"三讲，把这条主线讲透，并用 **health-rag** 仓库做了完整落地。**从 0 到 1 搭起来不难，难的是每一步都"有迹可循"、每个选择都有"为什么"。**

# 附录：常见 Q&A

**Q：RAG 和微调怎么选？**
A：知识更新频繁、要求可溯源 → RAG；模型风格/领域能力需要固化 → 微调。可组合使用。

**Q：为什么不用关键词检索（BM25）？**
A：BM25 字面匹配，同义词/口语化就失效。语义检索（向量）理解"意思"。两者可做混合检索增强召回。

**Q：向量数据库怎么选？**
A：规模小 → 嵌入式（ChromaDB）；规模大、要求高可用 → Milvus/Qdrant/ES。匹配规模即可。

**Q：怎么保证回答可信？**
A：三层保障——① 检索只喂相关资料；② Prompt 强制"基于资料回答"；③ 每次返回引用来源 + 分步 trace，可审计可追溯。

**Q：敏感数据安全吗？**
A：文档/向量全部本地，只有"上下文 + 问题"发给云端 LLM。如需绝对不出内网，可换本地模型（硬件要求更高）。
